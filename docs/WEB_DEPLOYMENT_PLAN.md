# Deploying the live EarthRisk demo

Status: deployed on 2026-11-15 as a passcode-protected demo at https://34-31-40-122.sslip.io/. The React frontend and Python API now run on the Google Cloud VM; the previous local API still serves its older local snapshot. The existing API explicitly binds to loopback, enforces local Host/Origin checks, uses in-process job queues, and is documented for a trusted local user. It is not ready to expose publicly as-is. Do not forward it through a public tunnel or proxy without first implementing and testing the public-service controls below.

## Recommended hackathon architecture

Use one Google Compute Engine VM with a persistent disk, a production web server for the built React files and HTTPS, a protected application API, and one supervised Earth Engine acquisition worker. This is the shortest migration of the current file-based pipeline: the worker and API can share the VM's local disk and completed tile index. This is near-real-time publication of completed historical-data processing, not a live satellite feed or instantaneous Earth Engine events.

1. Create a VM in `tactical-attic-456217-t0` with a persistent disk sized for the complete raw GLDAS inputs, raw MODIS archives, processed tiles, indexes, caches, operating system and growth; allow for a substantial safety margin. A point-in-time inventory on 2026-11-15 was about 715 MB GLDAS raw, 423 MB MODIS raw, 1.5 GB processed fine data, and 58 MB regional data, and is still growing. The existing worker stops when free disk falls below 20 GiB. Persistent Disk retains data across instance restarts; configure separate backups and deletion protection as appropriate. [Google Compute Engine disk documentation](https://docs.cloud.google.com/compute/docs/disks/persistent-disks).
2. Use the VM's attached service identity and Google Application Default Credentials for Earth Engine; register/enable the project and grant the identity the necessary Earth Engine and service-use permissions. Do not copy a user's OAuth token or service-account JSON key into the image or repository. [Earth Engine service accounts](https://developers.google.com/earth-engine/guides/service_account).
3. Clone the reviewed code, provision the Python and Node dependencies, and build `frontend/`. Git alone does not contain all currently generated tiles or local caches. Copy the required actual source files, pilot/collection releases and complete global tile directories to durable storage. Adapt or rebuild manifests containing absolute local source paths and verify each hash; preserve source archives. Make an initial copy while the local worker continues, then stop the local worker at cutover, copy the last completed immutable releases/index, verify them, and start exactly one writer on the VM. Do not run two processes that write the same index or tile concurrently.
4. Add and test a production HTTP entrypoint. Serve the frontend and `/api` from the same HTTPS origin; keep provider keys in server-side secret management. Do not simply relax the existing local server's Host/Origin checks. Add a suitable public request boundary with authentication or another deliberate access policy, rate limits, strict input validation, timeouts, and bounded persistent queues; protect expensive Earth Engine, Tavily and model calls against uncontrolled use. Preserve explicit user initiation for AI research and avoid automatic provider calls during map browsing.
5. Run the API and one acquisition worker under a supervisor that restarts failures, and monitor logs, disk, request errors, Earth Engine usage and cloud costs. Set budget notifications; an alerts-only budget does not cap spending. If available and suitable, evaluate a spend-cap budget. [Google Cloud budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets).
6. Publish a DNS name and TLS certificate, configure the HTTPS web server, test the deployed site from a separate device, and then share the URL. Verify real observations, on-demand research, polling, restart/recovery, access limits, and source provenance without putting credentials in browser bundles.

## How updates reach visitors

The current worker retrieves one tile at a time, publishes completed tile files and atomically replaces the local index. The API reads that index; the browser currently polls the first 1,000-cell summary page every 20 seconds. Completed batches are ordered newest first so recent tiles can appear on that page. The browser then runs its own screening using cached observations. A tile therefore usually appears only after processing, index publication, a poll and browser-side computation; exact latency depends on load. Results already open in a user's panel are not currently pushed to that panel automatically.

The first-page limit is a material constraint: most completed cells will eventually be outside the visible set. Build a viewport/bounds-based paginated map endpoint and cache/invalidate by data version before claiming complete global map updates. Newly available points can remain gray until their local browser screening finishes. Southern Alberta is currently queued first using the approximate Natural Earth boundary between 49° and 52.5° N; one-degree work tiles may also cover nearby areas.

## Alternative: Cloud Run and Cloud Storage

For a more scalable deployment, package the API separately for Cloud Run, place immutable tile releases and versioned manifests in Cloud Storage, and run acquisition in a separate durable worker/job with a single-writer protocol. Publish the manifest only after all tile objects are uploaded. Cloud Run containers use disposable filesystems; persistent data and caches need external storage, and its ingress container must listen on the injected `PORT` on `0.0.0.0`. Cloud Storage volume mounts and object storage are not a drop-in replacement for all current POSIX file writes, locks, `Path.replace`, source absolute paths, or in-process job state; adapt and test those semantics. [Cloud Run overview](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract), [Cloud Storage consistency](https://docs.cloud.google.com/storage/docs/consistency).

## Active deployment (2026-11-15)

The `earthrisk-demo` VM in `us-central1-a` runs the local API, passcode gateway, HTTPS Caddy proxy and the sole global acquisition worker as systemd services. The static external IP is reserved. The gateway requires a passcode, uses a signed secure cookie, checks POST origins and applies bounded login, data and research request rates. Provider credentials and passcode/session secrets live in root-managed `/etc/earthrisk/` files and must not be added to Git. The user's local generated passcode copy is in ignored `.cache/deployment/private.env`. The local world worker was stopped at cutover; do not restart it against the live dataset.

The initial data snapshot and a final 12-tile delta were copied with checksum verification. The VM worker uses its attached `earthrisk-demo` service account, not the user's local OAuth token, and prioritizes southern Prairies then Canada. New tile data stays on the VM; the older local data copy is not automatically synchronized. To inspect services, use `gcloud compute ssh earthrisk-demo --project=tactical-attic-456217-t0 --zone=us-central1-a --command='systemctl is-active earthrisk-api earthrisk-gateway earthrisk-worker caddy'`. To see acquisition status, inspect the worker journal and `/opt/earthrisk/data/processed/fine/global/index.json` as the `earthrisk` user.

To publish frontend-only changes, build `frontend/` and run `deploy/publish_frontend.sh` from an authenticated workstation. This publishes assets first and switches the HTML entrypoint last, retaining older hashed assets for existing sessions. Server-side code, credentials, and datasets are not updated by that command.

The VM, persistent disk, reserved IP, network transfer and provider requests can incur charges. Stopping the VM interrupts acquisition and serving; the persistent disk and reserved address may still incur charges. The demo uses a third-party `sslip.io` DNS hostname and automatic public TLS; use a team-controlled domain for a durable deployment. The current first-1,000-cell map limitation and non-calibrated modeled screening caveats remain.
